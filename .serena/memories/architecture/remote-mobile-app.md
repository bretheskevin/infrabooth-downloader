# Remote Mobile App — src-remote/

## Overview
A standalone React mini-app for phone browser remote control of the desktop app.
- No Tauri APIs, no desktop stores
- CAN reuse shadcn/ui components from `@/components/ui/*` (shares `@/` -> `../src/*` alias + node_modules): already uses `Button`, `SearchBar`, and `Tabs` (underline variant). Radix deps like `@radix-ui/react-tabs` are available. Prefer reusing the desktop component to match its exact styling rather than hand-rolling a lookalike.
- Connects via WebSocket (RemoteState pushes, RemoteCommand sends) and REST search
- Entry: `src-remote/index.html` (Vite root = `src-remote/`)

## Build Wiring
- `vite.remote.config.ts` — Vite config, root: `src-remote`, output: `src-tauri/remote-dist/`
- `src-remote/tsconfig.json` — type-check config for `src-remote/` + `src/lib/remote-protocol.ts` (paths: `@/*` -> `../src/*`, `@remote/*` -> `./*`). NOTE: there is NO `tsconfig.remote.json` — that name is stale.
- `tsconfig.json` — `src-remote` in exclude so main typecheck ignores it
- `tailwind.config.js` — includes `./src-remote/**/*.{ts,tsx}` in content

## Backend routes (src-tauri/src/services/remote.rs)
One shared router builder serves two listeners: the opt-in phone remote (`0.0.0.0`, `RemoteServerState`/`RunningServer` = shutdown + port only) and the auto-started Raycast local API (`127.0.0.1`, see `mem:architecture/raycast-extension`). Pushed state lives in the managed `RemoteHub` (independent of either listener), so `push_remote_state` feeds both. `/api/state` (GET, last pushed `RemoteState` JSON, 503 before first push) and `/api/command` (POST, body relayed raw to `events::REMOTE_COMMAND` like the WS path) exist on both listeners.
Axum handlers follow: token check -> get client_id/auth -> call service -> `Json(...)`. Query structs consolidated by shape: `TokenQuery` ({token}, used by ws/selections/library-artworks/state/command), `StreamableQuery` ({token, stream}, used by library/liked-tracks), `SearchQuery` ({q, token, limit?, offset?}; `page()` defaults 20/0, limit clamped 1–50), `ResourceQuery` ({id, secret, token}, used by library-artwork), `PlaylistTracksQuery` ({id, secret, token, stream}). Routes: `/api/search`, `/api/search-playlists`, `/api/search-albums` (playlist/album search map `ArtistPlaylist` -> `library::LibraryPlaylist` via `artist_playlist_to_library`), `/api/library`, `/api/liked-tracks` (reuses `crate::commands::library::load_liked_tracks`), `/api/playlist-tracks` (backed by `PlaylistTracksCache`, 10 min TTL + per-playlist fetch lock), `/api/library-artwork`, `/api/library-artworks` (NDJSON stream of resolved missing artworks), `/api/selections`, `/api/resolve-link` (`LinkQuery {url, token}`, backed by `services/resolve_link.rs`: validates, expands `on.soundcloud.com` short links, then `fetch_track_info`/`fetch_playlist_info`; 400 invalid link, 502 fetch error, otherwise internally tagged JSON `{kind:\"track\",track}|{kind:\"playlist\",playlist}` with raw `secret_token`/`download_url`; no sign-in required). With `stream=true`, library/liked-tracks/playlist-tracks answer NDJSON via `stream_ndjson`: one `batch` line per page, then `done` (full ordered list) or `error`. Library, liked-tracks, selections and library-artworks return 403 when signed out (`authorize_signed_in`). Playlist/album search reuses the existing `search::search_playlists`/`search_albums` services (also used by desktop).

## Stable link + standalone web app
- The phone-remote URL (`http://<lan-ip>:<port>/?t=<token>`) is stable across desktop restarts: `services/remote_link.rs` persists `{port, token}` in `remote-link.json` (app data dir, written via shared `services/private_file.rs` `write_atomic_private`, also used by the Raycast discovery file; `write_off_thread` wraps it in `spawn_blocking` with error logging and `describe_io_error` formats kind/os_error/Display — reuse both instead of hand-rolling). `start_server` loads it (missing/corrupt/empty token → `RemoteLink::fresh()`, port 0), `bind_lan` retries the saved port while busy, then falls back to a random port with a warn log (kind/os_error/Display) and the new port is saved. The Raycast local API (127.0.0.1) keeps its own per-launch token.
- `reset_remote_link` command (`remote::reset_link`) stops the server, persists a fresh token + random port and restarts if it was running, returning `Option<RemoteServerInfo>`. Gotcha: `start_server` / `reset_link` / `stop_server` all hold the `RemoteServerState` tokio mutex for the whole stop→bind→serve→register sequence (helpers `stop_running` + `start_with_link(&mut slot, ..)`); releasing it between stop and start lets a concurrent stop land during the port-retry window and orphan a running server. A start while running restarts on the saved link. If reset's restart fails the old token is already rotated, so the store clears `serverInfo` and `RemoteControlSettings` flips `remoteControlEnabled` off (same as a failed enable). `generate_token` lives in `remote_link.rs` (Raycast imports it from there, no remote↔remote_link cycle); `RemoteLink`'s `Debug` redacts the token. Desktop UI: "Reset link" button + `ConfirmDialog` in `RemoteControlSettings` (store `resetLink`), shown only while the server runs.
- `src-remote/index.html` has the iOS standalone tags (`apple-mobile-web-app-capable`, `mobile-web-app-capable`, `black-translucent` status bar, title, `apple-touch-icon` from `src-remote/public/apple-touch-icon.png`, `viewport-fit=cover`) and deliberately NO web manifest: the token comes from `?t=` in `App.tsx`, so a static `start_url` would drop it. Safe-area insets: `RemoteApp` container top padding, nav bottom padding, `NowPlayingPanel` header/bottom padding.
- Fullscreen button in `VisualizerControls`: supported → toggle; unsupported and not `isStandaloneWebApp()` (in `useFullscreen.ts`) → button toggles the inline `visualizerFullscreenHint` (Share → Add to Home Screen); standalone → hidden.

## Protocol
- Shared types in `src/lib/remote-protocol.ts` (imported via `@/lib/remote-protocol`)
- `RemoteState.isSignedIn` (bool) is pushed from the desktop `useRemoteBridge.buildRemoteState()` reading `useAuthStore`; a subscription re-pushes on auth change. Remote UI gates library nav + search mixes on it.
- Search track endpoints return Rust `TrackInfo[]` snake_case (artwork_url, permalink_url, waveform_url, duration in ms, user.username, user.id); playlist/album endpoints return `LibraryPlaylistJson[]`
- `RemoteCommand.downloadTrack` has optional `outputDir`, `secretToken`, `downloadUrl`; `downloadPlaylist {title, tracks: TrackInfo[], outputDir?}` carries raw backend tracks. The bridge routes it to `features/queue/utils/startPlaylistDownload` (shared with `useLibraryDownload`) and it is a no-op with `logger.warn` when `isDownloadQueueBusy` (`features/queue/utils/queueBusy.ts`).
- `RemoteState.downloadPath` / `downloadQueueBusy`: the bridge pushes on settings `downloadPath` change and on queue busy-flag flips via `subscribeToStoreChanges`. New `RemoteState` fields must be added to the factories in `src-remote/lib/__test__/playToggle.test.ts` and `raycast/src/lib/__test__/queueSections.test.ts`.
- CSS vars for theming: --bg, --bg-card, --bg-input, --text, --text-muted, --accent, --border

## Spectrum relay + fullscreen visualizer
- Opt-in per socket: phone sends text `{"type":"setSpectrum","enabled":bool}` (`RemoteSocketControl` in `remote-protocol.ts`); `remote.rs` `handle_incoming_text` consumes it (NEVER relayed to `REMOTE_COMMAND`) and `apply_spectrum_toggle` subscribes/drops a per-socket `spectrum_tx` receiver. Subscriptions die with the socket, so `useRemoteSocket` re-sends `setSpectrum` in `onopen` while enabled (`setSpectrumEnabled`).
- Frames: `RemoteHub.spectrum_tx` (broadcast, capacity 4, `Bytes`), fed by `spectrum.rs` `run_worker` via `remote::publish_spectrum` — no-op when `receiver_count()==0`. Each frame is `Message::Binary` of exactly `REMOTE_SPECTRUM_BAND_COUNT` (24) bytes, `round(clamp(band,0,1)*255)`. Frames stop when the worker's silence gate stops emitting, so the client shows its idle look. Raycast never sends `setSpectrum`, so it never gets binary frames.
- Client: `useRemoteSocket` sets `binaryType='arraybuffer'`; binary → `src-remote/lib/spectrumFrame.ts` `decodeSpectrumFrame` (`/255`) → shared `src/lib/spectrumBus.ts` `emitSpectrum` (same Set pub/sub as the desktop analyzer, no React state); text → `RemoteState` as before.
- UI: `src-remote/features/visualizer/` — `VisualizerScreen` (tap reveals auto-hiding `VisualizerControls`, horizontal swipe cycles styles via `hooks/usePointerGesture.ts` + `utils/gesture.ts`), `VisualizerCanvas` + `utils/renderFrame.ts` (rAF, DPR resize, smoothing with `src/lib/spectrumBars.ts`, idle blend), pure renderers `renderers/{bars,mirrored,radial,wave,idle}.ts` (shared `applyGlow` in `renderers/palette.ts`, bar column layout + fill in `renderers/columns.ts` `fillColumns`; lookup in `renderers/index.ts`; ordered style list `VISUALIZER_STYLE_IDS` in `remote-protocol.ts`; `cycleStyle` + `VisualizerToggle` type in `utils/visualizerSettings.ts`). Panel header icon buttons use shared `src-remote/components/PanelIconButton.tsx`. One shared set of settings lives in the desktop settings store (`visualizerSettings`, sanitized on rehydrate), is pushed to every remote via `RemoteState.visualizer`, and is changed only from the controls overlay by sending `RemoteCommand` `setVisualizerSettings` (the bridge sanitizes it with `sanitizeVisualizerSettings` and stores it, so all remotes update live). Types, `VISUALIZER_STYLE_IDS`, `DEFAULT_VISUALIZER_SETTINGS` and `sanitizeVisualizerSettings` are in `src/lib/remote-protocol.ts`. `useVisualizerSettings(state, send)` derives settings from `state.visualizer` (no local state, no optimistic override). Settings: style, track info overlay, blurred artwork background (blurred `<img>` behind the canvas — never backdrop-filter over a live canvas), color from artwork (`useArtworkColor`, falls back to `--primary`). Hooks `useWakeLock`, `useFullscreen`, `useAutoHide`. `VisualizerControls` header has a Maximize/Minimize toggle (`toggleAppFullscreen` + `useIsFullscreen` via useSyncExternalStore on `fullscreenchange`) (see the standalone section for the unsupported/iPhone behavior), so users can re-enter fullscreen after leaving it.
- Entry: AudioLines button in `NowPlayingPanel` header (`onOpenVisualizer`). `visualizerOpen` lives in `RemoteApp`, which calls `requestAppFullscreen()` inside the click handler (user gesture required) and keeps the visualizer mounted while disconnected (the "Reconnecting…" screen only shows when it is closed) so a Wi-Fi blip doesn't kick a wall monitor out.
- Limits: `navigator.wakeLock` needs a secure context, and the remote is plain `http://<lan-ip>`, so wake lock is usually a no-op on phones. iPhone Safari has no element fullscreen (feature-detected, skipped).
- `src-remote/tsconfig.json` has no jest-dom types: component tests use plain DOM assertions.
- i18n keys are flat `remote.visualizer*` (remote `t()` expects a flat `remote` string map).
