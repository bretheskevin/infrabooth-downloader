# Raycast Extension — raycast/ + local API

## Shape
- `raycast/` is a Raycast Store extension (author `kandid`, name `infrabooth-downloader`, macOS only). It imports shared code through tsconfig `paths` (`@/*` -> `../src/*`, `@remote/*` -> `../src-remote/*`; mirrored as aliases in `vitest.config.mts`): protocol types from `@/lib/remote-protocol`, `TrackInfo` from `@/bindings`, `mapTrack` from `@remote/lib/trackMapping`. `lib/mapping.ts` only holds the Raycast-side playlist/mix mappers. Store publishing copies only `raycast/`, so these cross-folder imports would have to be vendored before a Store publish.
- Root `tsconfig.json`, `vitest.config.ts` and `eslint.config.js` exclude `raycast/`. It has its own `node_modules`, Raycast eslint config and scripts (`npm run lint` / `npm run build` inside `raycast/`). Never run `ray develop` / `npm run dev` there.
- `platforms: ["macOS"]`: the desktop local API only starts on macOS. Keep it unchanged.
- Commands: `search` (view), `now-playing` (view) and `download-link` (view, `Form`). There is deliberately NO menu-bar command, because the user relies on macOS's built-in media controls and wanted a Raycast version of `ExpandedBar.tsx` instead.
- `now-playing` is a `view` command, not a menu bar. It is a `List` with `isShowingDetail` (Clipboard History layout): the queue is the list on the left, the player is the shared detail pane on the right. There is no pushed queue view (the old ⌘U `QueueList` was removed). `useLiveState` subscribes to the desktop's existing `GET /ws?token=` state stream (push) instead of polling `/api/state`, so Next/Previous, track end and desktop-side changes show instantly. It uses Node's global `WebSocket` (no `ws` dep): `@raycast/api` declares `engines.node >=22.22.2` and `ray build` targets `node22.22.2`, where the global is on by default. Each connect attempt re-reads `raycast.json` (token rotates every app start). Missing file / refused / 401 / close all map to `{ running: false }` (a value, never a toast) and reconnect with backoff [1,2,4,8,8]s, reset on open. On open it waits ~250 ms for the server's initial frame before emitting `{ running: true, state: null }`: open and the first frame arrive in separate macrotasks, so emitting null on open flashes "Nothing playing". Emissions are deduped by JSON snapshot; `isLoading` is derived (`live === undefined`). Commands still go through `POST /api/command` via `sendControl` (no post-command refresh); never send commands over the WS. `now-playing` itself does not poll, but `getState()` (`GET /api/state`) exists in `api.ts` and `download-link` uses it for `downloadPath` / `downloadQueueBusy`. `ApiError.detail` carries the plain-text error body of any non-OK response. Layout: the left list shows the WHOLE queue, split by the pure helper `lib/queueSections.ts` `buildQueueSections(state)`, which mirrors the desktop `useQueueInteraction` section logic: an untitled history section (indices before `cursor`), "Now Playing" (the current track, item id `String(cursor)`, selected by default via `selectedItemId`), then "Next up" (`manualQueueCount` items after the cursor), "Queue" (the rest before the station) and "Autoplay Station" (last `stationQueueCount` items), empty sections omitted. Indices are clamped into contiguous ranges (manual first, station start clamped to `>= manualEnd`), so a cursor inside the station part or oversized counts never duplicate/drop rows. Deliberate deviation: "Queue" is always titled in Raycast (the desktop hides that header when there are no manual items) because an untitled section after "Now Playing" reads as part of it. Labels are hardcoded English strings from `en.json` (`player.nextUp` / `queueSection` / `stationSection`); never import locales. Each row's id is its real queue index, its icon is the small artwork (fallback `Icon.Music`), its `title` is the track name prefixed `${index + 1}. ` on every row except the current one (absolute queue index + 1, matching `QueuePanelItem`; history and all upcoming sections included, no relative numbering, no per-section restart). The current "Now Playing" row is the plain title with no number, matching the desktop, which shows a music icon there instead of a number. The number goes in the title because `List.Item` has no number prop and a title prefix survives tail truncation in the narrow column. Each row's `subtitle` is the artist and `keywords` holds the artist so built-in filtering also matches artists. Rows have no accessories (Raycast keeps accessories full width in detail mode and truncates the title instead). Every row gets the SAME `List.Item.Detail` built from the current track (`NowPlayingDetail`): markdown is artwork (100×100) as its own paragraph, then ONE paragraph of `**title**`, artist, inline-code progress line joined by hard breaks (`"  \n"`). Keep it this compact: the detail markdown area has a fixed height above the metadata and scrolls otherwise, and `##` headings / blank-line paragraphs add too much vertical margin; metadata (rendered under the markdown in a List detail) is three labels Status / Volume / Shuffle. `isShowingDetail` is only set when a track is playing; app-not-running and nothing-playing are `List.EmptyView`s with `OpenAppAction`. `NowPlayingActions` takes the row's `track` + queue `index`: on every non-current row (history included) the primary ↵ is "Play This Track" (`skipTo` index) followed by Play/Pause (⌘↵); on the current row ↵ is Play/Pause. ⌘D downloads the selected row's track. `RemoteState.shuffle` mirrors the player's `isShuffled`, and `toggleShuffle` is a protocol command. Volume ±10 % is on ⌥⌘↑/⌥⌘↓ because ⌘↑/⌘↓ are Raycast section-jump/scroll keys. Action titles avoid "Up"/"Off" because `prefer-title-case` lowercases them.

## download-link command
- Sends `downloadTrack` (outside the queue; fills `secretToken` / `downloadUrl` from the resolved raw track) for tracks and `downloadPlaylist` (raw `playlist.tracks` forwarded untouched as `TrackInfo[]`, so it equals "Download all") for playlists.
- Refuses a playlist in Raycast when `downloadQueueBusy` is true.
- Sends `outputDir` only when the picked folder differs from `downloadPath || ~/Downloads`; it never changes the app setting.
- Pure helpers live in `lib/downloadLink.ts` and `lib/resolveLink.ts`, which must not import `@raycast/api` (stubbed in Vitest). Resolution is `hooks/useLinkPreview.ts` (300 ms debounce).
- Layout: a `Form`. The `SoundCloud Link` text field shows `typedLink ?? clipboardLink ?? ""` (pre-filled from the clipboard when it holds a SoundCloud link); the resolve error goes in the field's `error`. `components/LinkPreview.tsx` renders two text rows (`Form.Description` with `title` = label left / value right): `Track` = `title · duration` + `Artist` = artist, or `Playlist` = `title · N tracks` + `Owner` = owner (the user wants the duration/count on the title row) (rows merged on purpose: Raycast form row spacing is fixed and not stylable, so fewer rows is the only way to make it compact). No artwork: forms cannot render images and only `Form.Dropdown.Item` / `Form.TagPicker.Item` accept an `icon`; the user rejected a dropdown-as-title hack and wants the title as plain text. Then a `Form.Separator` (the user wants this horizontal divider kept), the `Form.FilePicker` folder (directories only, default = app `downloadPath`, override applies to this download only) and a `Destination` description (`~`-shortened; kept because the picker only shows the folder name). A Form cannot place blocks side by side; the user tried a `List` + detail two-column layout and reverted to this Form.
- ↵ before the link resolves toasts the blocked reason ("Still checking the link…" / the error / "Paste a SoundCloud link first").

## Desktop side (src-tauri/src/services/raycast.rs)
- `init()` is called from `lib.rs` setup and runs on macOS only. If `/Applications/Raycast.app` or `~/Applications/Raycast.app` exists, it starts the local API on `127.0.0.1:0` (`remote::start_local_api`) and writes `<app_data_dir>/raycast.json` `{port, token}` (0600, atomic temp+rename). There is no settings toggle. The token rotates every start. `remove_discovery_file` deletes it on `RunEvent::Exit` (wired in `lib.rs` `.run(|app, event| ...)`; NotFound is ignored), so a stale port is never handed out after a clean quit. A crash can still leave it behind, and Raycast then maps the refused connection to app-not-running.
- `LocalApiState.active` is set synchronously in `init()` before the async listener spawn, so the frontend's one-shot `is_local_api_active` query never races it.
- Gotcha: `RemoteHub` stores state with `watch::Sender::send_replace`. Plain `send` drops the value when there are no receivers, which is the case at startup.

## Frontend
- `useRemoteBridge` is active when `serverInfo` (phone) OR `useLocalApiActive()` (TanStack Query on `commands.isLocalApiActive`, `staleTime: Infinity`) is true.
- `downloadTrack` from a remote (Raycast or phone) calls `applyDownloadEvent` (`src/hooks/useDownloadState.ts`) with `status: 'downloading'` before `downloadTrackFull`, so desktop `TrackRow`s show the spinner and then follow the backend `download-progress` events like an in-app download; a failure sets `failed` only if the row is still `downloading`.
- `RemoteCommand` has `queueTracks` (Raycast "Add to Queue" on playlists/albums) and `toggleShuffle`. `RemoteState.shuffle` is built from `isShuffled`; `RemoteState.manualQueueCount` / `stationQueueCount` mirror the player store counts (Raycast needs them for the queue sections). `isPositionOnlyChange` compares `isShuffled`, `manualQueueCount` and `stationQueueCount` so a change to any of them pushes immediately instead of waiting for the 500 ms throttle. Raycast imports the shared `@/lib/remote-protocol` types directly (tsconfig `paths` `@/*` -> `../src/*`), so any new `RemoteState` field only needs adding to the `makeState` factory in `src-remote/lib/__test__/playToggle.test.ts` (typecheck fails otherwise).
